Study 02 · Multi-agent underwriting · measured

The same applicant, a hundred times

A rules engine gives the same answer every time. A language model samples one answer from a distribution — so asking twice can give twice the answers. This study runs the identical underwriting case through the system up to 100 times, records every decision, and treats the spread as something an actuary can measure, price and govern. The headline: variance is not noise, it concentrates — and the way you build around the model matters more than the model.

Why I ran this at all

Underwriting is a profession with a signature on the decision. Any AI in that loop has to answer a question that a demo never has to: if you run this case again tomorrow, do you get the same answer — and if not, what does the difference cost?

So the reference system — a multi-agent underwriting engine with Medical, Financial and Compliance agents debating over a deterministic rule base — is not just a demonstration of an architecture. It is an instrument: a place where a stochastic model can be asked the same question repeatedly and made to show its distribution. The report I wrote from it makes the argument I now make everywhere: a model whose output you have measured is safer than one you have not. Variance is measurable, understandable and manageable — and the third word is the point.

What this is, and is not

A reference system, not production: illustrative rules, synthetic applicants, one model (Qwen3.6-35B-A3B), one serving stack. On referred cases the LLM is the authority — there is no answer key — so this framework measures consistency, not accuracy. That distinction is deliberate: consistency is measurable today, and it is a precondition for everything else.

Method: a Monte Carlo of decisions

The technique is repeated invocation — run the same agent on the same applicant many times, record every decision, describe the distribution. Three decision paths are isolated so that variance can be attributed:

Three applicant profiles span the risk spectrum, plus a fourth engineered to make both agents uncertain at the same time. For each scenario the framework records the tier distribution (e.g. loading 74 %, standard 26 %), the consistency rate (share of runs on the modal decision), Wilson 95 % intervals — chosen over the Wald interval because it behaves correctly near 0 % and 100 % — and the failure rate, how often the model returns something the system cannot read.

The five findings

1 · Variance concentrates at the decision boundary

This is the finding that changed how I design. The spread is not scattered evenly across cases; it clusters exactly where a human underwriter would also hesitate.

Design consequence

If uncertainty concentrates at thresholds, the routing rule writes itself: route by distance from the decision boundary, not by case type. A clear case can be automated with a straight conscience; a borderline case is exactly where a human belongs in the loop — and that is a routing rule you can implement, monitor and price, not a slogan.

Corroborating evidence from a separate 50-run session (4c): material evidence changed the decision in 100 % of runs on every path, while irrelevant evidence changed it in 0 % — a false-positive rate of 0/50. The model is not merely reactive; on these tests it did not invent a reason to move.

2 · Temperature is a decision control, not a noise dial

The intuition “lower temperature, lower variance” is wrong in an important way.

  • T = 0 changed the answer, not just the consistency. On the high-risk profile, T = 0 returns a flat loading (100 %); T = 0.1 returned decline 58 % / loading 42 %. Turning the dial to zero produced a materially different underwriting decision — through a one-line configuration change that no reviewer would flag as a model change.
  • T = 1 does not become random. The borderline profile is still 83 % loading at temperature 1.0. The answer space is a handful of tiers and the model's own reasoning anchors it.

Governance consequence

Temperature and seed belong in the model-risk register as governance parameters: documented, versioned, tested for their effect on decisions. Reproducibility is not correctness — a fixed seed can make a wrong answer perfectly repeatable.

3 · Architecture beat the model

On the profile engineered to be genuinely borderline for both agents, the combined Medical + Financial debate returned loading in 100 of 100 runs. Not because the agents are individually stable — the Medical agent varies about 20 % on that profile — but because the orchestrator takes the most conservative view: the highest risk tier wins. The Financial agent always says loading, so taking the higher tier each time sets a floor that soaks up the Medical agent's swinging between standard and loading.

Design consequence — and the honest caveat

The combination rule is a control surface, and it is often a cheaper one than changing the model. But it is not free: a most-conservative floor buys stability by systematically pushing outcomes conservative, and in this system the Financial agent's reluctance to ever say decline means the floor can also mask a genuine escalation the Medical agent does reach. That is a risk-appetite decision somebody should make explicitly and sign, not a side-effect of an orchestrator default.

4 · Failures are stochastic too

Two operational findings that never appear in a benchmark table but decide whether a deployment survives contact with a production queue:

1

Malformed output. Now and then the model returns text the system cannot parse cleanly — wrapped in markdown, or carrying invalid control characters. The fallback keeps the refer tier, which is safe, but it is also variable: the same input sometimes produces a valid decision and sometimes a fallback. A fallback rate is therefore part of the decision distribution, not a footnote under it.

2

Failure under load. When the reasoning model was called with several requests in parallel it could get stuck in a thinking loop — emitting / characters and returning nothing. Running requests one at a time removed it. That is a real capacity limit to design around, and it means concurrency is a test variable, not a deployment detail.

5 · The variance you do not control is the largest

Everything above is variance within a fixed configuration. The larger risk sits outside it: three parties can each move the output distribution, and the deploying team may not be told.

Who else is holding a dial
partywhat they controlhow your output moves
Model developerweights, fine-tuning, alignment, versioninga model served under an unchanged name is not guaranteed to be the same model over time
API / inference providerhardware, quantisation, dynamic batching, routing, capacity substitutionthe same weights give different outputs depending on how they are served; batch size shifts with live traffic, which is why even a hosted T = 0 API is rarely bit-for-bit reproducible
The companyweights and every setting if self-hosted; sampling settings if an API; sometimes almost nothing if closed vendor softwareone line — temperature 0.1 → 0.3, an edited instruction — silently shifts the decision distribution
The variance you measured is only valid for the exact configuration you tested. Repeated-run testing is therefore an ongoing control, not a one-off exercise.

This is the same wall the A/E benchmark hit from a completely different direction. There: a harness tuned for one model loses accuracy on the next, so the model-and-harness pair must be re-measured. Here: a variance profile describes a configuration, so the pair must be re-measured after any change. Two independent studies, one governance rule — which is why it appears on the ecosystem page as the rule that binds every layer.

What I ask a model-risk pack to contain

01

Variance published beside accuracy. “How often is it right” and “how stable is it” are not independent: if the same case can return a different answer next time, accuracy is itself a distribution. A model that averages 90 % while swinging on borderline cases is not the same instrument as a steady 90 %.

02

A model-and-configuration inventory. Exact version or snapshot, vendor, deployment environment, and every output-affecting setting — without it, a variance number describes an unknown, drifting object.

03

Temperature and seed as versioned parameters with their measured effect on decisions, not as incidental config.

04

A recurring re-test as the drift alarm. Vendors update models quietly; the repeated-run test is the early-warning system that keeps “the model still behaves as we understood it” a true statement.

05

Named conservatism. If a combine rule pushes decisions conservative, the appetite decision is written down, signed, and priced — not inherited from a default.

Limitations I want on the record

  • Consistency, not accuracy. On referred cases there is no ground truth, so nothing here shows the model is right — only how steady it is. That is why the A/E benchmark exists: it supplies a generated answer key so accuracy can be scored.
  • One model, one serving stack, one temperature by default. Qwen3.6-35B-A3B at 0.1, with a sweep at 0.0 / 0.1 / 1.0 to characterise sensitivity. Other models may behave differently.
  • Fixed, illustrative profiles. Three profiles plus one engineered borderline case, not a sample of an applicant population.
  • Illustrative rules. Publicly documented underwriting principles, not a complete manual.
  • Cost is real. A hundred runs per case buys evidence a single shot cannot; the report says plainly that this belongs in standard validation rather than one-off assurance.
